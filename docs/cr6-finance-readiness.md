## Source of truth and lifecycle

1. Staff-associated `journey_supplier_allocations` record service, supplier, quantity, rate snapshot, currency, supplier cost and optional manual selling price. A pricing plan or custom rate can feed an allocation; CR5 requires verified rates before real use. Allocation `supplier_cost` is an expected cost, not cash paid.
2. `allocationCommercialSnapshot` reads the authoritative rows and active `tour_pricing_config` on the server. `calculateAllocationCommercials` sums active allocation costs, operations, administration and contingency into internal cost; applies fixed/percentage service fees; then prices against a **gross-margin** target. Explicit service selling prices act as a manual selling floor. The result includes actual gross profit and actual margin. A margin is profit divided by selling price; markup is profit divided by cost. The code's target is margin, not markup. No active proposal-API discount operation exists. The dormant package-engine adjustment type is not passed by the live package service, so it is not an approved discount workflow.
3. Proposal generation rejects incomplete allocation scope, missing service rate/quantity, missing cost or selling price, mixed allocation currencies, and now missing relevant commercial settings. It validates deposit and due-date arithmetic before saving versioned commercial and customer snapshots. The accepted proposal version is immutable; later allocation changes do not resync its account basis.
4. A draft/sent/accepted proposal does not by itself record money received. The existing accounting integrity commands create/activate the account and supplier settlements on the first positive traveller deposit. The traveller pays The Ceylon Edition, which pays suppliers; no traveller-to-supplier payment path was found. `journey_accounts` and posted `accounting_transactions` are financial truth; receipts/refunds/settlements derive collected, outstanding, payable and paid positions. Enquiry/journey operational status remains separate.
5. Payment, supplier settlement, waiver and refund commands are service-side, RBAC checked, idempotency guarded and audited with immutable posted transaction/reversal semantics. Supplier cost, margins, bank/payment references and private finance notes are excluded from the customer-safe proposal DTO. Finance permissions differ from journey-designer permissions. Public and unauthenticated admin boundaries remain protected.

## Precision, currency and schedule limits

The application uses JavaScript `number`, rounds displayed/calculated totals to two decimals, and uses PostgreSQL unconstrained `numeric` for important monetary columns/RPC amounts. Tests show the current calculator rounds `0.1 + 0.2` to `0.30`, but this does **not** prove end-to-end cent precision: direct database commands and some API input schemas can accept a third decimal, while database comparisons use small tolerances. This is a material finance-schema gap. Do not silently change historical rows or money types during CR6.

The proposal enforces one allocation currency; account settlement enforces its account currency. No FX conversion, rate source, conversion-time snapshot or reproducible historical FX calculation exists. A controlled launch therefore needs a founder-approved single traveller/supplier settlement currency and a policy for any supplier invoicing in another currency; do not infer an exchange rate. The current staging configuration says USD but contains no approved values or real rates.

The proposal supports a deposit amount plus deposit and balance due dates, with the balance derived as total minus deposit. CR6 rejects an over-total, fractional-cent or negative deposit and reversed dates. It does **not** have an enforceable arbitrary milestone schedule, due-date collection engine, automatic reminders or payment-provider integration. Cash receipt is manually recorded through guarded accounting commands. Historical sent customer snapshots can show paid amount as of document generation, not a live bank balance; the account ledger is authoritative for current payment status. No deposit percentage, supplier payment timing, cancellation charge, tax, payment-provider fee or refund policy has been approved in this audit.

## CR6-R1 cent-precision remediation candidate

The R1 migration `202609230001_cr6_cent_precision.sql` is an additive, staging-only schema gate. It uses explicit `CHECK (value = round(value, 2))` constraints rather than changing the monetary representation to integer minor units. That preserves signed accounting differences, nullability, defaults, existing monetary values and the current `numeric`/JavaScript application contract. It rejects non-finite `numeric` values. Seven legacy `numeric(p,2)` columns are converted to unconstrained `numeric` with their former magnitude bound retained, so a direct sub-cent write is rejected rather than silently rounded. The pre-existing proposal-invalidation trigger on journey benefits is recreated identically within the same atomic migration because PostgreSQL prevents changing the type of a column named in its `UPDATE OF` list.

The protected columns cover catalogue rates (accommodation, experience, guide, vehicle and pricing plans), journey/public estimate amounts, partner commercial fees, DMC pricing configuration, supplier-cost lines and allocations, proposal totals and acceptance total, journey account balances and differences, benefits, cancellation and recoverability amounts, settlements and posted accounting transactions. The migration deliberately excludes quantities, percentages, margin ratios, route distances, image focal coordinates and physical/fuel efficiency factors. Known money-valued JSON keys are checked recursively in enquiry estimates, allocation rate snapshots, proposal allocation/commercial/customer/sent snapshots and the accepted account quote snapshot. It does not rewrite historical snapshots or financial rows.

The four service-side finance commands taking numeric amounts and the allocation JSON command ultimately write protected columns; sub-cent durable writes must fail even if a caller bypasses HTTP validation. Staff-facing request validators now reject sub-cent deposits, supplier costs and selling prices, proposal optional items and commercial overrides, receipts, waivers, settlements, reversals, cancellation charges/refunds and benefit rates before calling the database. The public enquiry API rejects sub-cent estimate bounds. The existing payment calculation still rounds computed commercial totals to cents. R1 does not introduce FX or currency-specific minor-unit rules: supported launch currencies are assumed to use two-decimal commercial precision. A future zero- or three-decimal currency requires a separate architecture decision.
